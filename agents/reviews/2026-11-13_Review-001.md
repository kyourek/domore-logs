### #1 [P2] Shape complex text before constructing glyph runs [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:132-163`; character mapping in `source/Domore.Logs.Windows/Windows/Controls/LogGlyphTable.cs:30-39`.
- Problem and trigger: The fast path treats any sequence whose UTF-16 characters exist in the font's character map as independently positioned glyphs and forces `bidiLevel: 0`. Character coverage does not establish that a sequence requires no shaping or bidirectional layout. For example, set the supported `FontFamily` property to Arial and log the Arabic word `سلام`: every character is mapped, so the fallback formatter is never used.
- Impact: Arabic text is rendered as isolated, unjoined characters in the wrong direction. Other sequences requiring shaping or positioning can also be affected. This makes valid localized log content incorrect precisely when the selected font supports its characters.
- Evidence: A dispatcher-thread probe rendered that word through the actual presenter and extracted the resulting `GlyphRunDrawing` objects. All characters, including the header, were mapped in Arial. The presenter emitted one 27-glyph run with bidi level 0; ordinary WPF `FormattedText` emitted a 23-glyph header run at level 0 and a 3-glyph Arabic run at level 1. The presenter's Arabic indices were `945,989,909,993`, versus the shaped run's `947,1020,993`. This is an observed rendering-data difference, not an assumed font fallback problem.
- Suggested resolution: Restrict direct character-to-glyph mapping to a proven simple-text subset and use WPF shaping for the remaining content, or obtain shaped glyph runs from WPF's text formatter before retaining them. Preserve the visible-line caching approach.
- Verification: Render Arabic with a font that maps all characters and compare glyph selection, joining, and direction with WPF text layout. Include combining sequences as well as the existing missing-glyph fallback case.

Resolution: `LogGlyphTable.IsSimple` (`source/Domore.Logs.Windows/Windows/Controls/LogGlyphTable.cs:36`) restricts direct character-to-glyph mapping to U+0020 to U+02FF (Latin, Latin Extended, IPA, spacing modifier letters) and the punctuation ranges U+2010 to U+2027 and U+2030 to U+205E. Every other character, including surrogates, combining marks, bidirectional controls, and complex scripts, now reports unmapped even when the font has a glyph, so its line is drawn through WPF text layout (`FormattedText`), which shapes and orders it. Visible-line caching is unchanged. The direct path still applies no kerning or ligatures; for the permitted characters that affects appearance in proportional fonts, not content or order.
Verification: Red/green. New `LogControlTest.ComplexScriptIsShapedWhenFontMapsEveryCharacter` (`tests/Domore.Logs.Windows.Tests/Windows/Controls/LogControlTest.cs:362`) sets Arial, asserts that Arial maps every character of the Arabic word U+0633 U+0644 U+0627 U+0645, logs it, and inspects the realized glyph runs. Against baseline `d873f62` it failed with no run at an odd bidi level; after the fix it passes. New `LogGlyphTableTest.CharactersRequiringLayoutAreUnmappedEvenWhenFontHasThem` (`LogGlyphTableTest.cs:22`) covers an Arabic letter, a Hebrew letter, a combining acute accent (U+0301), and a right-to-left mark (U+200F); all four cases failed before the fix and pass after it. `SimpleCharactersRemainMapped` confirms that `a`, U+00E9, and an em dash (U+2014) keep the direct path. `dotnet build tests/Domore.Logs.Windows.Tests/Domore.Logs.Windows.Tests.csproj -c Release` (SDK 10.0.404) succeeded with 0 warnings and 0 errors across `net462`, `net48`, `net8.0-windows`, and `net10.0-windows`; `dotnet test` on the same project passed 61 of 61 tests on each of the four frameworks.

### #2 [P2] Preserve the tail of long lines that require font fallback [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:182-193`.
- Problem and trigger: A single missing character or surrogate pair sends the entire display line to `FormattedText`, where `MaxLineCount = 1` is applied. WPF can internally break very long input even without a caller-supplied wrapping width. The remaining text is then silently omitted. A log message containing 10,000 ASCII `x` characters followed by an emoji reaches this path with the default Consolas font.
- Impact: The end of an otherwise retained log line cannot be read, including by scrolling horizontally. Adding an emoji to a long line can cause most of its text to disappear, and the horizontal extent describes only the retained prefix.
- Evidence: The actual presenter was measured and arranged at 600 by 100 DIPs, and its retained drawings were inspected. The 10,000-character and 100,000-character messages, each followed by an emoji, both emitted exactly 9,600 glyphs and the same `ExtentWidth` of approximately 63,328 DIPs, despite formatted input lengths of 10,025 and 100,025 UTF-16 code units. The shorter 1,000-character control case emitted the expected 1,024 glyphs. The omitted suffix is absent from the drawing itself, so viewport clipping does not explain the result.
- Suggested resolution: Format and retain the entire logical line, processing text formatter continuation or safe shaping-aware chunks and placing the resulting runs horizontally. Simply removing the line-count restriction would put continuation text on additional rows without updating the line model.
- Verification: Render a line longer than 9,600 characters with a fallback character and a distinctive trailing marker. Verify that the marker is drawn, can be reached by horizontal scrolling, and the full line remains on one display row.

Resolution: The fallback path in `LogPresenter.DrawFormatted` (`source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:233`) formats a line in pieces of at most 4,096 characters, which is below WPF's internal break of about 9,600, and draws them side by side on one row. `FindPieceEnd` (`:207`) ends a piece after whitespace in the second half of the window when possible. Otherwise it ends at the latest position that does not split a surrogate pair, precede a combining mark or format character, or follow a zero-width joiner (`CanBreakBetween`, `:191`). Each piece is placed at `Baseline - formattedText.Baseline`, so pieces share the line's baseline even when a fallback font has different metrics. The line's width, and therefore the horizontal extent, is the sum of the pieces. Breaking at whitespace keeps shaping within words intact; a right-to-left phrase spanning a piece boundary is ordered within each piece rather than across the whole phrase.
Verification: Red/green. New `LogControlTest.LongFallbackLineIsDrawnInFullOnOneRow` (`LogControlTest.cs:381`) logs 10,000 `x` characters, an emoji, and `END` with the default Consolas font. It asserts that the realized glyph runs contain all 10,000 `x` characters, end with `END`, share one baseline, and occupy one buffered line. Against baseline `d873f62` it failed with fewer than 10,000 `x` characters drawn; after the fix it passes. `dotnet build tests/Domore.Logs.Windows.Tests/Domore.Logs.Windows.Tests.csproj -c Release` (SDK 10.0.404) succeeded with 0 warnings and 0 errors across `net462`, `net48`, `net8.0-windows`, and `net10.0-windows`; `dotnet test` on the same project passed 61 of 61 tests on each of the four frameworks.

### #3 [P2] Apply the line bound before accumulating the delivery batch [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogControl.cs:75-89`; expansion in `source/Domore.Logs.Windows/Windows/Controls/LogLineFormatter.cs:42` and `:92-103`.
- Problem and trigger: `Deliver` expands every pending entry into the persistent `DeliveredLines` list before `Presenter.Append` skips lines beyond `LineLimit`. Pending entry count is bounded, but each entry can contain an arbitrary number of message lines. `DeliveredLines.Clear()` subsequently clears references without reducing the list's backing capacity. One multiline entry can therefore allocate and permanently retain a large staging array even when `LineLimit` is 1.
- Impact: A large multiline log incurs unnecessary dispatcher allocations and work for discarded display lines, and leaves the control's memory consumption proportional to its largest delivery batch for the rest of its lifetime. Bursts with many multiline entries can multiply this overhead and undermine the intended bounded viewer.
- Evidence: Splitting a one-million-newline entry produced 1,000,001 `LogLine` values, a list capacity of 1,048,576, and 67,109,232 allocated bytes (approximately 64 MiB) on the probe thread. A separate invocation of the actual private `Deliver` method with a one-million-message entry and `LineLimit = 1` confirmed one retained presenter line but staging `Count = 0` and `Capacity = 1,048,576` after `Clear()`. That backing array alone occupies approximately 32 MiB on this x64 runtime. The input entry was allocated before the delivery measurement; the line-descriptor overhead is introduced by the viewer.
- Suggested resolution: Bound intermediate line storage by `LineLimit`, retaining only the newest descriptors while processing a batch, or split directly into a bounded ring buffer. Avoid keeping a staging array sized to discarded historical bursts.
- Verification: Deliver an entry and a batch containing far more lines than a small configured limit. Verify newest-line ordering and that staging capacity/allocation is bounded by the configured limit rather than the expanded batch size.

Resolution: The staging list was removed. `LogControl.Deliver` (`source/Domore.Logs.Windows/Windows/Controls/LogControl.cs:74`) now calls `LogLineFormatter.Split` (`LogLineFormatter.cs:96`), which adds line descriptors directly to the presenter's bounded `LogLineBuffer`, then calls `LogPresenter.LinesAdded` (`LogPresenter.cs:374`). The ring buffer discards the oldest descriptors as it fills, so storage never exceeds `LineLimit`, however many lines one entry or batch contains. `LogPresenter.LinesChanged` (`:111`) now derives the scroll adjustment for discarded lines from the change in `LogLineBuffer.FirstSerial`, replacing the count that `Append` used to supply. Work per entry is still proportional to its line count, through constant-time buffer appends.
Verification: Red/green on .NET 8 and .NET 10. New `LogControlTest.LargeMultilineEntryKeepsNewestLinesWithoutStagingEveryLine` (`LogControlTest.cs:397`) sets `LineLimit = 2`, logs one 200,000-line message, and measures `GC.GetAllocatedBytesForCurrentThread` across the dispatcher flush. Against baseline `d873f62` it failed the under-1-MiB allocation assertion; after the fix it passes and retains only the two newest lines in order. That allocation API is unavailable on .NET Framework, so on `net462` and `net48` the test checks only line retention and order. New `LogLineFormatterTest.SplitKeepsNewestLinesWithinBufferLimit` (`LogLineFormatterTest.cs:67`) covers splitting several messages into a two-line buffer. `dotnet build tests/Domore.Logs.Windows.Tests/Domore.Logs.Windows.Tests.csproj -c Release` (SDK 10.0.404) succeeded with 0 warnings and 0 errors across `net462`, `net48`, `net8.0-windows`, and `net10.0-windows`; `dotnet test` on the same project passed 61 of 61 tests on each of the four frameworks.

### #4 [P2] Handle page-mode mouse wheel settings before multiplying the line count [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:386-391`.
- Problem and trigger: `MouseWheelUp` and `MouseWheelDown` multiply `SystemParameters.WheelScrollLines` directly by line height. Windows represents the "One screen at a time" setting as `WHEEL_PAGESCROLL` (`UINT_MAX`, returned as -1 in the signed WPF value). Consequently, the two methods reverse direction instead of scrolling a page.
- Impact: Users with this supported Windows mouse setting move down when wheeling up and move up when wheeling down. At the end of the log, wheeling up is clamped at the end, preventing normal wheel navigation into history.
- Evidence: [Windows SystemParametersInfo documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow) defines page scrolling for this sentinel; [WPF SystemParameters source](https://source.dot.net/PresentationFramework/System/Windows/SystemParameters.cs.html) shows `WheelScrollLines` returning the cached signed native value. A probe substituted -1 in that cache within its own process after initializing it, called the actual presenter methods, and restored the value in `finally`. From an offset of 400 DIPs, `MouseWheelUp` moved to 416 and `MouseWheelDown` moved to 384. No Windows preference or registry value was changed.
- Suggested resolution: Detect the page-scroll sentinel and call `PageUp` or `PageDown`; use line-height multiplication for nonnegative line counts. Consider the documented page behavior when the requested line count exceeds the viewport as well.
- Verification: Exercise page mode from the middle and end of a scrollable log. Up must decrease the offset by a viewport, down must increase it, and ordinary positive line-count settings must retain their expected direction and distance.

Resolution: `MouseWheelUp` and `MouseWheelDown` now get their distance from `LogPresenter.GetWheelDistance` (`source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:444`). It returns the viewport height for a negative `SystemParameters.WheelScrollLines` (the `WHEEL_PAGESCROLL` sentinel), and otherwise the line count times the line height, capped at one viewport, as Windows documents for counts larger than the visible lines. The sign of the distance no longer depends on the setting, so Up always moves up and Down always moves down.
Verification: Red/green. `GetWheelDistance` was first extracted with its original arithmetic, without changing behavior, so the setting could be supplied without patching WPF's process-wide cache. New `LogControlTest.PageModeWheelScrollsOneViewportInWheelDirection` (`LogControlTest.cs:417`) checks page mode (-1), three lines, a count larger than the viewport, and zero. Against the extracted baseline arithmetic it failed in page mode (a negative distance); after the fix it passes. The test exercises the distance calculation rather than real mouse input. `dotnet build tests/Domore.Logs.Windows.Tests/Domore.Logs.Windows.Tests.csproj -c Release` (SDK 10.0.404) succeeded with 0 warnings and 0 errors across `net462`, `net48`, `net8.0-windows`, and `net10.0-windows`; `dotnet test` on the same project passed 61 of 61 tests on each of the four frameworks.
