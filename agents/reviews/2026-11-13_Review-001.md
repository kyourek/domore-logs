## Findings

### #1 [P2] Preserve right-to-left ordering across formatter continuations [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:122-123` (target revision).
- Problem and trigger: A visible log message containing a sufficiently long continuous Hebrew or Arabic run crosses the text formatter's forced line boundary even with `NoWrap`. `Draw` formats each continuation and places it after the previous continuation by increasing `x`. WPF resolves bidirectional order within each formatted fragment, but these fragments represent successive logical portions of the same display row. Placing every fragment left to right moves a later logical RTL portion to the right of an earlier portion, instead of preserving the whole run's right-to-left visual order.
- Impact: The viewer displays long RTL messages in the wrong order when the user scrolls horizontally. This affects the documented support for bidirectional Unicode text and complete long lines; the stored text and copied text remain in logical order. Ordinary short RTL messages and long Latin messages do not expose the problem.
- Evidence: An isolated STA/.NET 10 probe referenced the target Release assemblies, appended one message consisting of `new string('\u05D0', 9000) + new string('\u05D1', 9000) + new string('\u05D2', 9000)`, and arranged the ordinary control at 600 by 100. Traversing its retained `GlyphRunDrawing` objects showed ALEF (`U+05D0`) run origins at x=4276.04..72860.32 and GIMEL (`U+05D2`) run origins at x=72991.91..177871.72. Thus every run containing the later GIMEL suffix lies to the right of every run containing the earlier ALEF prefix. A continuous same-level RTL run requires the suffix to appear to the left of the prefix. The increasing-x continuation loop directly explains the observed ordering. The existing `ArabicUsesWpfShapingAndDirection` test only exercises a short Arabic word; `LongUnicodeLineRetainsTrailingMarker` exercises Latin text plus emoji, so neither covers this combination.
- Suggested resolution: Preserve paragraph-level bidirectional visual order when positioning formatter fragments. Resolve the complete row's bidi runs and position the fragments according to that visual order, retaining WPF shaping and fallback within those runs, or use a layout path that can preserve the complete unwrapped paragraph's ordering. Do not assume that all logical continuations can be appended at increasing x; simply reversing every continuation would also mishandle mixed LTR/RTL content.
- Verification: Add coverage for long Hebrew/Arabic runs crossing multiple formatter boundaries and for mixed Latin/RTL messages. Check visual positions of distinguishable prefix and suffix runs, along with full character preservation and the horizontal extent. A short RTL control case should continue to pass.

- Resolution (2026-11-13, uncommitted patch on `windows-2`): `LogPresenter.Draw` retains the direct WPF `TextLine.Draw` path for complete rows. For rows spanning formatter continuations, it collects WPF-shaped indexed glyph runs in logical source order, obtains whole-paragraph embedding levels through Windows Uniscribe `ScriptItemize` in `LogBidi.cs`, applies bidi visual reordering across the entire row, and positions the retained glyph runs accordingly. Full embedding levels are necessary because WPF exposes the nested European numeric run as drawing level 0. `LogScriptItem.cs` matches the native eight-byte structure; caller-owned output storage grows and retries when needed. WPF still supplies shaping and font fallback. No public API or package dependency was added.
- Regression evidence: Before production edits, the initial two `LongRtlRunKeepsVisualOrderAcrossContinuations` cases and `LongMixedDirectionGroupsKeepLatinSeparatorBetweenThem` built successfully and failed for their visual-order assertions on .NET 10 (3 failed, 0 passed).
