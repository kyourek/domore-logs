## Findings

### #1 [P2] Preserve ordering of right-to-left passages that still span a piece boundary [Accepted limitation]

- Status: Accepted limitation; previously acknowledged remaining limitation of `agents/reviews/2026-11-14_Review-001.md` issue #1.
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:249-252`; independent layout and placement at `:277-288` (target revision).
- Problem and trigger: When a right-to-left passage has no qualifying left-to-right letter after whitespace in the second half of an 8,192-character piece, `FindPieceEnd` falls back to any whitespace. `DrawFormatted` then independently formats the pieces as left-to-right paragraphs and appends each after the preceding piece. This reverses the required ordering of the pieces within the passage. Increasing the limit fixed the earlier 5,000-character example but leaves longer passages affected, including some that WPF can format correctly in one call.
- Impact: Valid Hebrew or Arabic log messages display their words in the wrong sequence across piece boundaries. The last word can appear at the right end of a long passage instead of its left end. Horizontal scrolling exposes the incorrect sequence; the copied logical text remains intact.
- Evidence: A new STA .NET 10 probe at the target revision used Arial at 12 DIPs and the ordinary subscription path: `Logging.For(typeof(Program)).Info("intro", text)`, followed by a dispatcher flush and layout. `text` was 2,200 repetitions of U+05D0 U+05D1 U+05D2 separated by spaces, followed by a space and U+05E9 U+05DC U+05D5 U+05DD. The message has 8,804 UTF-16 code units and its indented display line has 8,806. Both the actual retained drawing and an unsplit WPF `FormattedText` reference contained all 8,806 code units, ruling out truncation. In the actual drawing, the right-to-left glyph run containing the distinct final word started at X 43,859.69 DIPs; in the reference, its run started at X 38.81. Independent chunk ordering places that final word at the opposite end of the passage. This is an observed remaining defect, not a regression in the already passing 5,000-character test.
- Suggested resolution: Preserve the full line's bidirectional ordering when placing pieces, rather than relying on whitespace alone. Format the whole line when the underlying formatter can handle it, and retain whole-paragraph directional context or resolve visual ordering before positioning pieces for longer lines. A larger fixed threshold alone moves the failure boundary.
- Verification: Compare the visual positions of distinct first and last words in the 8,804-character passage with unsplit WPF output. Also exercise right-to-left passages longer than WPF's internal line limit, mixed-direction passages, and existing long-tail coverage. Preserve the fixed 5,000-character scenario.

Decision: Not fixed; accepted as a limitation. Correct ordering of a single right-to-left passage that is longer than a piece needs the Unicode bidirectional algorithm applied across the whole row. WPF does not provide that beyond its internal line limit of about 9,600 characters, and .NET exposes no public API for the per-character direction data it would need. Raising the piece size only moves the failure point and risks reaching WPF's own line break. The limitation affects only a right-to-left passage with no left-to-right letter in the last 4,096 characters of a piece, in a line longer than 8,192 characters, which is rare for log output and rarer still for this project's expected content. It is documented here and in `2026-11-14_Review-001.md` issue #1. Revisit it if long right-to-left log lines become a real use case; the likely approach is to run a bidirectional algorithm over the row and place pieces by visual order.

### #2 [P2] Keep supplementary emoji modifiers with their base at piece boundaries [Resolved]

- Status: Resolved.
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:202-211`; boundary selection at `:255-258` (target revision).
- Problem and trigger: `CanBreakBetween` examines only the next UTF-16 `char` for a low surrogate, combining-mark/format categories, or a preceding zero-width joiner. It permits a boundary before the high surrogate of an emoji skin-tone modifier. A base emoji and its modifier can therefore be formatted in separate pieces even though they must be shaped together. No whitespace boundary rescues a long unbroken message.
- Impact: A supported emoji sequence is displayed as an unmodified emoji followed by a separate skin-tone swatch, with a different glyph count and horizontal advance from the original message. The same sequence renders correctly when moved away from the arbitrary piece boundary.
- Evidence: The same probe logged `new string('x', 8188) + char.ConvertFromUtf32(0x1F44D) + char.ConvertFromUtf32(0x1F3FD) + "END"` as the second message of an `ILog.Info` call, with `FontFamily = "Segoe UI Emoji"` and `FontSize = 12`. Two indentation spaces put the boundary immediately after U+1F44D THUMBS UP SIGN and before U+1F3FD EMOJI MODIFIER FITZPATRICK TYPE-4. The actual drawing emitted base glyph 1213 at the end of the first piece and separate modifier glyph 1082 at the start of the second; an unsplit WPF reference emitted the single combined glyph 1216. Its suffix run contained 19 glyphs, while the equivalent actual suffix contained 20 across the two pieces. Moving the prefix to 8,186 or 8,190 characters restored combined glyph 1216 in the actual presenter; only the across-boundary position split it. All content is present: the defect is the loss of combined shaping. Glyph IDs identify this host's installed font and are not universal constants.
- Suggested resolution: Select boundaries using grapheme/emoji sequence rules compatible with all supported target frameworks. At minimum, decode supplementary scalars and prevent a break between an emoji modifier base and its modifier; inspecting the high surrogate's Unicode category cannot establish a valid boundary. Keep this correction separate from whole-paragraph bidirectional ordering.
- Verification: Render the sequence immediately before, across, and after the 8,192-character boundary, with no intervening whitespace. Each case must retain the same combined emoji glyph and advance as an unsplit reference. Repeat for each supported framework, including .NET Framework, whose text-element segmentation may differ from modern .NET.

Resolution: `CanBreakBetween` is replaced by `LogPresenter.CanBreakAt` (`source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:224`), which decodes the supplementary code point that starts at the candidate break with `CodePointAt` (`:210`) and refuses a break before it when it is an emoji skin-tone modifier (U+1F3FB to U+1F3FF). The existing checks remain: a low surrogate, a combining, enclosing or format character, and a character that follows a zero-width joiner. Two related sequences of the same kind are also kept together: the second regional indicator of a flag pair, and the tag characters (U+E0020 to U+E007F) of subdivision flags. The decoding uses surrogate arithmetic only, so it behaves the same on every target framework and does not depend on text-element segmentation. `FindPieceEnd` (`:285`) takes the new check; no other behavior changed, and lines that fit in one piece or break at whitespace do not use it.
Verification: Red/green for the modifier. New `LogControlTest.EmojiModifierStaysWithItsBaseAtAPieceBoundary` (`tests/Domore.Logs.Windows.Tests/Windows/Controls/LogControlTest.cs:615`) logs a single message of `x` characters, U+1F44D, U+1F3FD and `END` with Segoe UI Emoji and requires the drawn glyph count to equal that of the same line formatted once by `FormattedText`. The header of a single-message line is 27 characters, so prefixes of 8,161, 8,163 and 8,165 place the break before, between and after the pair. Before the fix, only the 8,163 case failed, with one extra glyph (8,195 against 8,194), as in the review; the cases before and after the boundary passed. After the fix all three pass on all four frameworks. `dotnet build --no-restore --configuration Release` of the whole solution (SDK 10.0.404) succeeded with 0 warnings and 0 errors, and `dotnet test` passed 81 of 81 tests in `Domore.Logs.Windows.Tests` on each of `net462`, `net48`, `net8.0-windows` and `net10.0-windows`, with the unchanged `Domore.Logs.Tests` still passing (300 passed and 3 skipped on `net462`, `net48` and `net8.0`; 302 passed and 1 skipped on `net10.0`). Flag-pair and tag-character handling follows the same code path but has no dedicated test, because Segoe UI Emoji draws flags as letters, so splitting a flag does not change the glyph count and the test would not fail without the fix. The test is skipped where Segoe UI Emoji is not installed.
