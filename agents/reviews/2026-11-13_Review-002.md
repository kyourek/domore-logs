### #1 [P2] Pin the presenter to left-to-right so log text is not mirrored in right-to-left UI [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:363-368` (constructor). The affected drawing is in `LogPresenter.cs:154-169` (glyph runs at bidi level 0) and `LogPresenter.cs:239-249` (`FormattedText` with `FlowDirection.LeftToRight`).
- Problem and trigger: `LogPresenter` draws its own text in left-to-right coordinates but inherits `FlowDirection` from its ancestors. When an application or any ancestor sets `FlowDirection="RightToLeft"`, which is the standard setting for Arabic or Hebrew localized WPF applications, WPF mirrors the element's coordinate space. The glyph runs and formatted text are then rendered horizontally flipped. WPF text elements avoid this by laying out with the element's flow direction; this presenter draws in fixed left-to-right coordinates.
- Impact: Every log line is unreadable in a right-to-left application: glyph shapes are mirrored and text runs right to left.
- Evidence: A .NET 10 probe under the ignored `out/review-002-probe` directory rendered a `LogControl` containing the line `ABCDEFG readable text 123` inside a `Border`, once with left-to-right and once with right-to-left flow direction, using `RenderTargetBitmap` at 400 by 40 DIPs. Comparing only non-background pixels:
  - The right-to-left rendering matched the horizontally flipped left-to-right rendering for 97.6% of text pixels, and matched the unflipped rendering for 4.1%.
  - A `TextBlock` with the same text and font, as a control, matched its flipped rendering for only 7.3%, so WPF keeps its text readable.
  - Setting `Presenter.FlowDirection = FlowDirection.LeftToRight` in the right-to-left case made the rendering match the normal left-to-right rendering for 95.0% of text pixels, and the flipped rendering for 4.0%.
- Suggested resolution: Set `FlowDirection = FlowDirection.LeftToRight` on the presenter, for example in its constructor. WPF then applies a counter-mirror at the presenter boundary, so lines remain readable and left-aligned while the surrounding template, including the scroll bars, follows the application's direction. Right-aligned, right-to-left log presentation would be a separate feature.
- Verification: Render the control inside a right-to-left parent and compare it with the left-to-right rendering. The text must match the unflipped rendering, not the mirrored one. Also confirm that horizontal scrolling still moves the text in the expected direction inside a right-to-left `ScrollViewer`.

Resolution: The `LogPresenter` constructor (`source/Domore.Logs.Windows/Windows/Controls/LogPresenter.cs:372`) sets `FlowDirection = FlowDirection.LeftToRight`, so an inherited right-to-left flow direction no longer mirrors the text the presenter draws in left-to-right coordinates. The surrounding template, including the border and the scroll bars, still follows the application's flow direction. Lines remain left-aligned; right-aligned presentation for right-to-left cultures is a separate feature and was not added.
Verification: Red/green. New `LogControlTest.TextIsNotMirroredInRightToLeftParent` (`tests/Domore.Logs.Windows.Tests/Windows/Controls/LogControlTest.cs:549`) renders one long log line with `RenderTargetBitmap` inside a left-to-right and a right-to-left `Border`, at horizontal offsets 0 and 150, and requires that more than 80% of the non-background pixels are identical. Scroll bars are hidden in the test because they follow the flow direction by design, and the offset 150 case covers scrolled text. Against baseline `b4e2369`, run in a temporary detached worktree that held the final test file, both cases failed, with 8.4% and 1.5% agreement; after the fix both pass. The earlier probe measured 95.0% agreement for the pinned presenter. `dotnet build --no-restore --configuration Release` of the whole solution (SDK 10.0.404) succeeded with 0 warnings and 0 errors, and `dotnet test` passed 65 of 65 tests in `Domore.Logs.Windows.Tests` on each of `net462`, `net48`, `net8.0-windows` and `net10.0-windows`, with the unchanged `Domore.Logs.Tests` still passing (300 passed and 3 skipped on `net462`, `net48` and `net8.0`; 302 passed and 1 skipped on `net10.0`). The scroll bar behavior in a right-to-left `ScrollViewer` was not separately inspected.

### #2 [P3] Copy retained text so a partly discarded entry is not kept whole [Resolved]

- Status: Resolved
- Location: `source/Domore.Logs.Windows/Windows/Controls/LogLine.cs:11-12` (descriptor fields `Entry` and `Message`). The descriptors are created in `source/Domore.Logs.Windows/Windows/Controls/LogLineFormatter.cs:42` and `:103` and retained by `source/Domore.Logs.Windows/Windows/Controls/LogLineBuffer.cs:39-55`.
- Problem and trigger: Each buffered `LogLine` holds a reference to its `ILogEntry` and to the complete source message string, then reads its own text segment from them when the line is drawn. When an entry has more lines than `LineLimit`, or straddles the oldest buffered position, the ring buffer keeps only some of its lines. The remaining descriptors still keep the entire entry alive, including every message string in `LogList` and the full text of a split message.
- Impact: Retained memory is not bounded by `LineLimit` and the retained lines' text. It can exceed that by the full size of the oldest, partially discarded entry. The excess is bounded, because lines are kept in order and only the oldest entry can be partly discarded. It is released once that entry's last buffered line is replaced. A large multi-line dump, such as serialized data or a long trace, can therefore stay in memory far beyond what the viewer displays.
- Evidence: A .NET 10 probe under `out/review-002-probe` created a `LogControl` with `LineLimit = 2`. It logged one 200,000-line message of 10,000,000 characters (about 19 MiB of UTF-16 text), which Domore.Logs delivered as 200,000 strings. A separate subscription captured a `WeakReference` to the delivered entry.
  - After the flush, the control buffered 2 lines, and the entry was still alive after a full blocking garbage collection.
  - After two further single-line entries replaced those lines and another full collection ran, the entry was no longer alive.

  Earlier designs stored only line text and did not retain the source entry.
- Suggested resolution: When `Split` adds lines of an entry that will be partly discarded, and in any case when the buffer discards the earlier lines of a retained entry, give the surviving descriptors standalone data:
  - a copy of the needed text segment, for example through `Substring`;
  - the header fields (date, severity, name), instead of the `ILogEntry` and the full message.

  A simple invariant: a descriptor may reference a shared message only while its whole entry is buffered. Keep the lazy text building for normal entries.
- Verification: Repeat the probe. With `LineLimit = 2`, a large multi-line entry must become unreachable after a full collection while its last two lines are still buffered, and those two lines must still render their original text.

Resolution: The root cause was the `ILogEntry` reference held by every buffered `LogLine`, which kept the entry and its whole `LogList` alive. `LogLine` (`source/Domore.Logs.Windows/Windows/Controls/LogLine.cs:13-21`) now stores only the date, severity, and name its header needs, which `LogLineFormatter.Split` (`source/Domore.Logs.Windows/Windows/Controls/LogLineFormatter.cs:96-98`) reads once per entry, and refers to its own message string. A buffered line therefore keeps alive only the text it displays. The suggested copying of line text was not added, because Domore.Logs already splits every string message on newlines (`source/Domore.Logs/Logs/LogFormatter.cs:15-21`), so lines of one entry do not share one large string. Residual case: output of a custom formatter registered with `Logging.Format` is not split by Domore.Logs (`LogFormatter.cs:115`). If such a message contains newlines, the viewer splits it into several lines that share that one string, and a surviving line keeps that one message alive. That is bounded to a single message and was left as is.
Verification: Red/green. New `LogControlTest.DiscardedLinesDoNotKeepSourceEntryAlive` (`LogControlTest.cs:559`) sets `LineLimit = 2`, logs one message of 20,000 lines while a capture subscription holds weak references to the delivered entry and its first message, and requires after a full collection that both are collected and the two newest lines are still buffered with their original text. New `LogControlTest.BufferedLinesDoNotKeepSourceEntryAlive` (`LogControlTest.cs:575`) logs three lines of 100,000 characters with the default limit, so the whole entry is buffered, and requires that the entry is collected and all three lines still render in full. Against baseline `b4e2369`, run in a temporary detached worktree that held the final test file, both failed with "The entry is kept by a buffered line"; after the fix both pass, as does the existing allocation test for large multi-line entries. The tests depend on optimized (Release) JIT lifetimes, so the helpers that build and log the message are not inlined; a Debug build can keep locals alive and is not supported by these tests. `dotnet build --no-restore --configuration Release` of the whole solution (SDK 10.0.404) succeeded with 0 warnings and 0 errors, and `dotnet test` passed 65 of 65 tests in `Domore.Logs.Windows.Tests` on each of `net462`, `net48`, `net8.0-windows` and `net10.0-windows`, with the unchanged `Domore.Logs.Tests` still passing (300 passed and 3 skipped on `net462`, `net48` and `net8.0`; 302 passed and 1 skipped on `net10.0`). The throughput benchmark from earlier in the session was not re-run after `LogLine` gained its three header fields.
